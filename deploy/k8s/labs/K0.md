# K0 — Cluster up

**Goal:** a running single-node k3s cluster and a working `kubectl`, and a mental model of what "a cluster" is on one machine.

## What this repo teaches here
- `deploy/k8s/host/k3s-config.yaml` — k3s is configured with a YAML file whose keys are CLI flags. We disable `servicelb` so nothing listens on the LAN, and keep a commented K12 CPU-manager line.
- `scripts/ubuntu-setup.sh` — copies the host config **before** installing k3s (k3s reads it at first start), then copies the admin kubeconfig to `~/.kube/config` with mode 600.

## Concepts
- **Node**: a machine that runs pods. Here: one node that is also the **control plane** (API server, scheduler, controller-manager, all inside the single `k3s` process, with SQLite/kine instead of etcd).
- **kubelet**: the agent on each node that turns PodSpecs into containers (via containerd).
- **Namespace**: a name scope for objects (not a security boundary by itself). Ours is `bench`.
- **kubeconfig / context**: which cluster + user + default namespace `kubectl` talks to.

## Try it
```bash
make setup-host                      # once; log out/in afterwards for the docker group
kubectl get nodes -o wide
```

myhost   Ready    control-plane,master   2m    v1.3x.y+k3s1   192.168.1.20   Ubuntu 24.04.x LTS   containerd://...
```

kubectl get pods -A                  # coredns, local-path-provisioner, metrics-server, traefik, helm-install-* (Completed)

```

## Break it on purpose
1. `sudo systemctl stop k3s`
2. `kubectl get nodes` → `The connection to the server 127.0.0.1:6443 was refused`.
3. `sudo k3s crictl ps 2>/dev/null || ps aux | grep containerd-shim | head` → the **containers are still running**: k3s deliberately leaves pods up when the service stops (so upgrades don't cause outages). Nothing can *change* them though: no scheduling, no restarts, no probes.
4. `sudo /usr/local/bin/k3s-killall.sh` really stops everything (this is what `make mode-compose` does).

**Recover:** `sudo systemctl start k3s && kubectl wait --for=condition=Ready node --all --timeout=120s`

## Check yourself
<details><summary>What runs in <code>kube-system</code>, and why there?</summary>

Cluster add-ons that k3s bundles: CoreDNS (Service DNS names like `postgres`), Traefik (Ingress controller), local-path-provisioner (creates PVs as directories on the node), metrics-server (CPU/memory for `kubectl top` and the HPA), and the helm-install jobs that installed Traefik. They live in `kube-system` by convention: infrastructure separated from apps so RBAC and cleanup (`kubectl delete ns bench`) never touch them.
</details>

<details><summary>When k3s is stopped, what fails and what keeps running?</summary>

Everything that needs the API server fails: kubectl, scheduling, controllers (no ReplicaSet reconciliation), probes acting on pods, Service endpoint updates. Already-running containers keep running, and existing iptables rules keep routing traffic, until `k3s-killall.sh` or a reboot.
</details>

<details><summary>Why copy kubeconfig to ~/.kube/config instead of using /etc/rancher/k3s/k3s.yaml?</summary>

The original is root-only (we set `write-kubeconfig-mode: "0600"`). A private copy lets your user run kubectl without sudo, and it is cluster-admin, so it must stay mode 600 and never be committed (`kubeconfig*` is in `.gitignore`).
</details>
