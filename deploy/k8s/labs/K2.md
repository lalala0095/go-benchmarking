# K2 — Postgres

**Goal:** a stateful database whose data survives pod restarts, configured by a Secret and a ConfigMap.

## What this repo teaches here
- `scripts/secrets.sh` — Secrets `postgres-credentials` and `gemini` from `.env`, via `kubectl create … --dry-run=client -o yaml | kubectl apply -f -` (idempotent "create or update"). Never committed.
- `scripts/sync.sh` → `base/generated/` — ConfigMap `db-init` from `db/init/*` (the same scripts Compose mounts), mounted at `/docker-entrypoint-initdb.d` with `defaultMode: 0755` so `05-apply.sh` is executable.
- `base/postgres/statefulset.yaml` — StatefulSet with `volumeClaimTemplates` (10Gi, `local-path`), the Compose `command` flags as `args`, `/dev/shm` as a memory-backed emptyDir, `pg_isready` probes over TCP.
- `base/postgres/service.yaml` — **headless** Service (`clusterIP: None`) named `postgres`.

## Concepts
- **StatefulSet vs Deployment**: stable pod names (`postgres-0`), ordered start/stop, one PVC per replica that follows the identity.
- **PV / PVC / StorageClass**: the PVC is a *request* ("10Gi RWO, class local-path"); the provisioner creates a PV (a directory under `/var/lib/rancher/k3s/storage/`) and binds them.
- **Secret vs ConfigMap**: same mechanics (env or files), but Secrets are kept out of `get -o yaml` by RBAC conventions and can be encrypted at rest. They are only base64 — not encryption.

## Break it on purpose
1. Write something: `kubectl -n bench exec postgres-0 -- psql -U bench -d dashboard -c "create table k2(x int); insert into k2 values (42);"`
2. Delete the pod: `kubectl -n bench delete pod postgres-0`, then `kubectl -n bench get pod -w` — it comes back with **the same name**.
3. `kubectl -n bench exec postgres-0 -- psql -U bench -d dashboard -c "select * from k2"` → `42`. The PVC outlived the pod.
4. Now delete the data for real: `make k8s-reset-db` (deletes the StatefulSet *and* PVC `data-postgres-0`; deleting the StatefulSet alone would keep the PVC). Then `make k8s-up OVERLAY=dev` — the init scripts run again on the empty volume and `k2` is gone.

**Recover:** step 4 already recovers. If the servers' DB looked broken meanwhile: `kubectl -n bench rollout restart deploy/go-server deploy/fastapi-server deploy/dashboard`.

## Check yourself
<details><summary>Why a StatefulSet, not a Deployment?</summary>

A Deployment's pods are interchangeable (random names, can briefly run two during a rollout, all share one PVC or none). A database needs a stable identity, exactly one writer on its volume, and a volume that stays bound to *that* identity across reschedules. A StatefulSet gives `postgres-0` + `data-postgres-0`, and its default rolling update stops the old pod before starting the new one.
</details>

<details><summary>When would you use an operator (e.g. CloudNativePG) instead?</summary>

When you need what a StatefulSet doesn't know about Postgres: replication and automatic failover, backups/PITR, major-version upgrades, connection pooling, monitoring. An operator encodes a DBA's runbook as a controller. For a single benchmark DB that we can recreate from init scripts, a StatefulSet is enough and more instructive.
</details>

<details><summary>Why do the probes use <code>-h 127.0.0.1</code>?</summary>

On first boot the image's entrypoint starts a temporary Postgres listening only on the unix socket while it runs the init scripts. A socket check would say "ready" mid-init; a TCP check only passes once the real server is up.
</details>

<details><summary>Why is <code>/dev/shm</code> an emptyDir with <code>medium: Memory</code>?</summary>

Container runtimes give 64 MiB of shared memory by default; Postgres uses it for parallel query workers. Compose had `shm_size: 1g`; Kubernetes has no such field, so we mount a tmpfs. Its pages count toward the container's memory limit.
</details>
