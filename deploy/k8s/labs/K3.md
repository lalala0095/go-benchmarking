# K3 — go-server

**Goal:** a stateless app as a Deployment behind a Service, with probes that mean the right thing.

## What this repo teaches here
`base/go-server/deployment.yaml` and `service.yaml`:
- **initContainer** `wait-for-postgres` (pgvector image, `pg_isready` loop): Kubernetes has no `depends_on`.
- **startupProbe** `/healthz` (2 s × 60): protects slow first boots; the other probes wait for it.
- **readinessProbe** `/healthz` (checks the DB): failing it removes the pod from the Service, nothing else.
- **livenessProbe** `/bench/ping` (no DB): failing it restarts the container.
- `envFrom` the `server-env` ConfigMap + `DATABASE_URL` built with `$(POSTGRES_USER)` expansion from the Secret.
- Service `go-server` selecting `app.kubernetes.io/name: go-server`, `targetPort: http` (a named port).

## Concepts
- **Deployment → ReplicaSet → Pod**: the Deployment manages ReplicaSets (one per pod-template version); the ReplicaSet keeps N pods alive.
- **Labels and selectors**: the only link between a Service/ReplicaSet and its pods.
- **Service DNS**: `go-server` → `go-server.bench.svc.cluster.local` → a ClusterIP → kube-proxy iptables DNAT → a Ready pod IP.
- **EndpointSlices**: the live list of Ready pod IPs behind a Service.

## Try it
```bash
kubectl -n bench get deploy,rs,pod -l app.kubernetes.io/name=go-server
kubectl -n bench describe pod -l app.kubernetes.io/name=go-server | grep -A3 -E 'Init Containers|Liveness|Readiness|Startup'
kubectl -n bench logs deploy/go-server -c wait-for-postgres     # "waiting for postgres" lines, then accepting connections
kubectl -n bench port-forward svc/go-server 8081:8080 &
curl -s localhost:8081/v1/info | jq .                            # runtime, version, limits
curl -s localhost:8081/healthz; curl -s localhost:8081/bench/ping
kill %1
kubectl -n bench get endpointslices -l kubernetes.io/service-name=go-server
kubectl -n bench run dns --rm -it --image=busybox:1.36 --restart=Never -- nslookup go-server   # a ClusterIP, not the pod IP
```

## Break it on purpose
1. Point readiness at a 404:
   ```bash
   kubectl -n bench patch deploy go-server --type=json \
     -p '[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/nope"}]'
   ```
2. A new pod starts but never becomes Ready (`0/1`), and thanks to `maxUnavailable: 0` the old pod keeps serving. In another terminal `kubectl -n bench get endpointslices -l kubernetes.io/service-name=go-server -w`: the new pod's address shows `ready: false`.
3. Now remove the safety net: switch to `Recreate` (kill all old pods first, then start new ones):
   ```bash
   kubectl -n bench patch deploy go-server --type=json \
     -p '[{"op":"replace","path":"/spec/strategy","value":{"type":"Recreate"}}]'
   kubectl -n bench rollout restart deploy/go-server
   ```
   The endpoint list empties: the only pod is `Running` but not Ready. `curl` through the Service (port-forward to `svc/go-server`) fails, and `kubectl -n bench describe pod -l app.kubernetes.io/name=go-server` shows `Readiness probe failed: HTTP probe failed with statuscode: 404`. Note: no restarts — readiness never restarts anything.

**Recover:** `make k8s-up OVERLAY=dev` — re-applying the manifest restores both the probe path and the strategy (`rollout undo` would only restore the pod template, not `spec.strategy`).

## Check yourself
<details><summary>Why must liveness not depend on the DB?</summary>

Liveness failure = restart. If liveness checked the DB, a 30-second Postgres blip (restart, failover, overload) would make *every* server pod fail liveness at once, and Kubernetes would restart all of them — turning a DB hiccup into a full outage plus a cold-start storm, and the restarts can't fix the DB anyway. Liveness should answer "is this process wedged?" only. Readiness may check dependencies, because it merely stops routing traffic.
</details>

<details><summary>What's the difference between startupProbe and a big initialDelaySeconds?</summary>

`initialDelaySeconds` is a fixed wait on every start, even fast ones. A startupProbe polls and hands over to liveness/readiness the moment it first succeeds, while still allowing a slow start up to `periodSeconds × failureThreshold` (2 min here).
</details>

<details><summary>Why does the initContainer use the Postgres image?</summary>

It needs `pg_isready`, and `pgvector/pgvector:pg17` is already on the node for the StatefulSet, so no extra pull. The server images are distroless (no shell).
</details>

<details><summary>What would break if the Service selector included <code>bench/target</code> and someone changed that label?</summary>

Selectors are immutable on Deployments, and a Service whose selector no longer matches has no endpoints. That's why our selectors contain only `app.kubernetes.io/name`, and the shared `part-of` label is added with `includeSelectors: false`.
</details>
