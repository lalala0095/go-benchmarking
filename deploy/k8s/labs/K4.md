# K4 — fastapi-server

**Goal:** the Python server with its worker count derived from its own CPU limit, and config delivered as files.

## What this repo teaches here
`base/fastapi-server/deployment.yaml` (same probes/rollout as K3), plus:
- `PY_WORKERS` from the **downward API**: `resourceFieldRef: {resource: limits.cpu, divisor: "1"}` — the CPU limit rounded *up* to whole cores (500m → 1, 2 → 2).
- `PROMETHEUS_MULTIPROC_DIR` on an `emptyDir` (each uvicorn worker writes metrics files there).
- The RAG corpus as a **ConfigMap volume** at `/corpus`. Keys can't contain `/`, so `sync.sh` stores `docs/01-PRD.md` as key `docs__01-PRD.md`, and the generated patch adds `items: [{key: docs__01-PRD.md, path: docs/01-PRD.md}, …]` so the tree matches Compose.

## Concepts
- **Downward API**: expose pod/container facts (name, namespace, labels, requests/limits) as env vars or files.
- **Config as env vs as volume**: env vars are fixed at container start; a mounted ConfigMap is a set of files that the kubelet refreshes (atomically, via a `..data` symlink swap) roughly within a minute.
- **emptyDir**: scratch space that lives exactly as long as the pod.

## Try it
```bash
kubectl -n bench exec deploy/fastapi-server -- env | grep -E 'PY_WORKERS|PROMETHEUS'
#   dev overlay (limit 500m) -> PY_WORKERS=1 ; bench overlay (limit 2) -> PY_WORKERS=2
kubectl -n bench exec deploy/fastapi-server -- ls -la /corpus /corpus/docs
#   /corpus: docs -> ..data/docs, ..data -> ..2026_…  (the symlink trick)
kubectl -n bench get cm -o name | grep rag-corpus
kubectl -n bench get deploy fastapi-server -o jsonpath='{.spec.template.spec.volumes[?(@.name=="corpus")].configMap.items[0]}'; echo
```

## Break it on purpose
1. Starve it of memory:
   ```bash
   kubectl -n bench set resources deploy/fastapi-server -c fastapi-server --limits=memory=128Mi --requests=memory=64Mi
   kubectl -n bench get pods -l app.kubernetes.io/name=fastapi-server -w
   ```
2. Watch `OOMKilled` → `CrashLoopBackOff`. `kubectl -n bench describe pod -l app.kubernetes.io/name=fastapi-server | grep -A5 'Last State'` shows `Reason: OOMKilled, Exit Code: 137`. Thanks to `maxUnavailable: 0` the old pod is still serving.
3. (Optional) Compare: `kubectl -n bench set resources deploy/go-server -c go-server --limits=memory=128Mi` — Go usually survives at idle. Why? (smaller runtime, no N worker processes each importing ADK).

**Recover:** `make k8s-up OVERLAY=dev` (re-applies the overlay's resources) or `kubectl -n bench rollout undo deploy/fastapi-server`.

## Check yourself
<details><summary>Why does ConfigMap-as-env need a restart, but a volume mount doesn't?</summary>

Environment variables are copied into the process at exec time; Linux has no way to change another process's environment afterwards. A ConfigMap volume is files that the kubelet re-syncs periodically (the app still has to re-read them). Exceptions: `subPath` mounts never update. In this repo we sidestep the question with **generated, hash-suffixed** ConfigMaps: any content change renames the ConfigMap, which changes the pod template and triggers a rolling restart — deterministic instead of "eventually".
</details>

<details><summary>Why compute workers from the CPU limit instead of hard-coding them?</summary>

So one image behaves correctly in every overlay: 1 worker with 1 CPU (no pointless context switching), 2 with 2. It's the Python equivalent of Go reading the cgroup limit for GOMAXPROCS. Note the rounding: a 1500m limit gives 2 workers that can only use 1.5 CPUs between them.
</details>

<details><summary>Why can't a ConfigMap hold a corpus of a few MB?</summary>

Objects are stored in the datastore with a ~1 MiB limit. We stop at 900 KB (`sync.sh` fails clearly); bigger corpora go through the servers' HTTP ingest API. We also apply with `--server-side`, because client-side apply copies the whole object into a 256 KiB annotation.
</details>
