# K5 — Dashboard

**Goal:** give the dashboard exactly the API permissions it needs, and reach it through an Ingress.

## What this repo teaches here
- `base/dashboard/serviceaccount.yaml` — identity `system:serviceaccount:bench:dashboard`; the pod gets a short-lived token mounted automatically, which `@kubernetes/client-node` uses (in-cluster config).
- `base/dashboard/role.yaml` — namespaced Role: pods get/list/watch/delete; deployments + deployments/scale get/list/patch; HPAs get/list/create/patch/delete; statefulsets get/list; `pods.metrics.k8s.io` get/list. Each rule is commented with the scenario that needs it.
- `base/dashboard/rolebinding.yaml` — binds the Role to the ServiceAccount.
- `base/dashboard/ingress.yaml` — Traefik rule `/` → `dashboard:3000`.
- `base/dashboard/deployment.yaml` — `PLATFORM=k8s`, `K8S_NAMESPACE` from the downward API, no Docker socket.

## Concepts
- **RBAC**: *who* (subject: user, group, ServiceAccount) may do *what* (verbs) on *which* resources (apiGroup + resource + optional subresource) *where* (Role = one namespace, ClusterRole = cluster-wide). Permissions are additive only; there are no deny rules.
- **Least privilege**: the dashboard can delete pods in `bench` but cannot read Secrets, touch other namespaces, or create Deployments.
- **Ingress vs Ingress controller**: the Ingress object is just a routing rule; Traefik (in `kube-system`) watches Ingresses and does the proxying.

## Try it
```bash
SA=system:serviceaccount:bench:dashboard
kubectl auth can-i delete pods          -n bench   --as=$SA   # yes
kubectl auth can-i patch deployments/scale -n bench --as=$SA  # yes
kubectl auth can-i get secrets          -n bench   --as=$SA   # no
kubectl auth can-i delete pods          -n default --as=$SA   # no  (Role is namespaced)
kubectl auth can-i --list -n bench --as=$SA
kubectl -n bench get ingress dashboard          # CLASS traefik, ADDRESS empty
make k8s-open                                   # port-forward svc/traefik 8080:80 (leave running)
curl -s localhost:8080/api/health               # in another terminal
curl -s localhost:8080/api/platform | jq .      # mode "k8s", limits, qos_class
```
From the Mac: `ssh -L 8080:localhost:8080 <user>@<ubuntu-host>` and open http://localhost:8080.

## Break it on purpose
1. Remove `delete` from the pods rule:
   ```bash
   kubectl -n bench patch role dashboard --type=json \
     -p '[{"op":"replace","path":"/rules/0/verbs","value":["get","list","watch"]}]'
   kubectl auth can-i delete pods -n bench --as=system:serviceaccount:bench:dashboard   # no
   ```
2. Run the **cold-start** scenario from the dashboard. It fails, and `kubectl -n bench logs deploy/dashboard | grep -i forbidden` shows a 403: `pods "go-server-…" is forbidden: User "system:serviceaccount:bench:dashboard" cannot delete resource "pods"…`. RBAC changes take effect immediately, no restart.

**Recover:** `make k8s-up OVERLAY=dev` (re-applies the Role).

## Check yourself
<details><summary>Why is the Traefik <code>LoadBalancer</code> Service <code>&lt;pending&gt;</code>?</summary>

A `type: LoadBalancer` Service asks *something* to provide an external IP. In clouds that's the cloud controller; in k3s it's `servicelb` (klipper-lb), which binds node ports 80/443 on every interface. We disabled it (`k3s-config.yaml`) so nothing is exposed to the LAN, so nobody fulfils the request and it stays `<pending>`. Traefik still works inside the cluster, and `kubectl port-forward` reaches it from localhost.
</details>

<details><summary>Why a Role and not a ClusterRole?</summary>

Everything the dashboard touches lives in `bench`. A ClusterRole+ClusterRoleBinding would grant the same verbs in every namespace, including `kube-system`. (A ClusterRole bound with a *RoleBinding* would also be namespaced; we just don't need a reusable role.)
</details>

<details><summary>Why is <code>deployments/scale</code> listed separately from <code>deployments</code>?</summary>

Subresources are authorized separately. `kubectl scale` and the HPA use the `scale` subresource; you can allow scaling without allowing arbitrary edits to the pod template (which would let you run any image).
</details>

<details><summary>Why no Docker socket in k8s?</summary>

Mounting the container runtime socket gives root on the node. In Kubernetes the API server is the control interface, and RBAC lets us grant a precise subset of it.
</details>
