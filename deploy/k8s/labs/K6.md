# K6 — Kustomize

**Goal:** one base, three environments, zero copy-paste; and deploy-time values without editing files.

## What this repo teaches here
- `base/kustomization.yaml` — `namespace:`, common `labels:` (with `includeSelectors: false`), `configMapGenerator` (`server-env`, `build-info`), `images:` placeholders, and a nested kustomization `generated/` + a generated patch.
- `overlays/dev`, `overlays/bench` — `resources: [../../base]` + a **strategic-merge patch** (`resources.yaml`) that only lists what changes.
- `overlays/scale` — stacks on `../bench`, adds `hpa.yaml`, and uses a **JSON 6902 patch** (`op: remove /spec/replicas`) on two Deployments selected by a regex target.
- `scripts/apply.sh` — a throwaway wrapper kustomization in `/tmp` adds `images:` (tag pinning) and `configMapGenerator … behavior: merge` (`GIT_SHA`, `.env` values). The repo stays clean.

## Concepts
- **Base / overlay**: overlays reference a base and transform it; they never copy it.
- **Strategic merge vs JSON 6902**: SMP looks like a partial object and merges lists by key (containers by `name`); JSON patch is explicit ops on paths (good for removals and list indexes).
- **Generators + hash suffix**: `server-env` becomes `server-env-5782bm4tbd`; references are rewritten; a content change ⇒ new name ⇒ rolling update.

## Try it
```bash
./deploy/k8s/scripts/sync.sh
kubectl kustomize deploy/k8s/overlays/dev   | less
diff <(kubectl kustomize deploy/k8s/overlays/dev) <(kubectl kustomize deploy/k8s/overlays/bench)
kubectl kustomize deploy/k8s/overlays/scale | grep -A3 'kind: HorizontalPodAutoscaler'
RENDER_ONLY=1 OVERLAY=bench TAG=abc1234 ./deploy/k8s/scripts/apply.sh | grep 'image: localhost'
kubectl diff -k deploy/k8s/overlays/bench           # what WOULD change in the live cluster (exit 1 = differences)
```
`kubectl diff` shows a tag change to `dev` and env/ConfigMap differences because the raw overlay lacks what `apply.sh` adds — that's expected; compare with `RENDER_ONLY=1 … | kubectl diff -f -`.

## Break it on purpose
1. In `overlays/dev/resources.yaml`, rename `name: go-server` (the Deployment patch) to `name: go-servr`.
2. `kubectl kustomize deploy/k8s/overlays/dev` → `Error: no resource matches strategic merge patch "Deployment.v1.apps/go-servr.[noNs]": no matches for Id …`. Kustomize refuses to silently drop a patch.
3. Rename a container instead (`- name: go-srv` under `containers:`): it renders **without error** and you get a *second*, broken container in the output. Strategic merge adds list items it can't match — always read the rendered output.

**Recover:** `git checkout deploy/k8s/overlays/dev/resources.yaml`

## Check yourself
<details><summary>When would you pick Helm instead?</summary>

Helm is a templating + packaging + release tool: good for distributing software to *other* people with many knobs (`values.yaml`), versioned charts, install/upgrade/rollback history, and dependencies (e.g. kube-prometheus-stack in K11). Kustomize is template-free patching of plain YAML: good for *your own* apps across a few environments, built into kubectl, and the rendered output is easy to review. Many teams use both (Helm for third-party charts, Kustomize for their own manifests or to patch a chart's output).
</details>

<details><summary>Why does <code>apply.sh</code> use a temp wrapper instead of <code>kustomize edit set image</code> in the overlay?</summary>

`kustomize edit` rewrites `kustomization.yaml` in place, which would dirty the git tree on every deploy (and different machines would commit different tags). A wrapper in `/tmp` that references the overlay keeps the repo as the source of truth and makes the tag a deploy-time input.
</details>

<details><summary>Why is <code>generated/</code> a separate kustomization instead of plain files?</summary>

Its file list depends on what's in `db/init/` and `corpus/`, so `sync.sh` writes the generator list too. Kustomize can't read files outside its root, so they must be copied in; and the folder is git-ignored so the copies never drift into commits.
</details>
