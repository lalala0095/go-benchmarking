# K7 — Resources and QoS

**Goal:** understand requests vs limits, get the Guaranteed QoS class for benchmark pods, and see CFS throttling with your own eyes.

## What this repo teaches here
- `overlays/bench/resources.yaml` — requests == limits for the servers and Postgres, including the `wait-for-postgres` initContainers (a pod is Guaranteed only if all its containers are). Integer CPUs so K12's static CPU manager could give exclusive cores.
- `overlays/bench/kustomization.yaml` — the CPU budget: limits 2 + 2 + 2 + 4 = 10 of 12 threads, leaving ~2 for OS, k3s and the desktop. The dashboard is deliberately **Burstable** (request 3.5, limit 4): with a 4-CPU request, a rolling update of a server would need 12.2 CPUs of requests and the surge pod would stay Pending forever.
- `overlays/dev` for contrast: requests < limits ⇒ **Burstable**.

## Concepts
- **request**: what the scheduler reserves (placement + CPU *weight* under contention). **limit**: the hard cap — CPU is throttled (CFS quota per 100 ms period), memory is OOM-killed.
- **QoS classes**: Guaranteed (req == lim for CPU and memory everywhere) > Burstable > BestEffort (nothing set). Under node memory pressure the kubelet evicts BestEffort first, Guaranteed last.
- **CFS throttling**: a 2-CPU limit = 200 ms of CPU time per 100 ms period across all threads. A burst of 8 threads uses it up in 25 ms and then *everything* waits ~75 ms — latency spikes even at low average CPU.

## Try it
```bash
make k8s-up OVERLAY=bench
kubectl -n bench get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
#   postgres-0 / go-server-… / fastapi-server-…  Guaranteed ; dashboard-…  Burstable
#   (re-run with OVERLAY=dev: all Burstable)
kubectl describe node | sed -n '/Allocated resources/,/Events/p'   # cpu requests ~9.7 (80%), limits 10
kubectl top pods -n bench                                           # metrics-server, ~15 s resolution
# cgroup view from inside a server (what bench_cgroup_* metrics read):
kubectl -n bench exec deploy/fastapi-server -- cat /sys/fs/cgroup/cpu.max /sys/fs/cgroup/cpu.stat
#   cpu.max "200000 100000" = 2 CPUs ; cpu.stat nr_throttled / throttled_usec
```
Then run the **cpu** scenario from the dashboard and watch `bench_cgroup_cpu_throttled_seconds_total` (or `throttled_usec` above) climb.

## Break it on purpose
1. Squeeze Go to half a core. First try only the limit:
   ```bash
   kubectl -n bench set resources deploy/go-server -c go-server --limits=cpu=500m
   ```
   The API server rejects it: `Invalid value: "2": must be less than or equal to cpu limit` — a request can never exceed its limit. Lower both (still Guaranteed, just smaller):
   ```bash
   kubectl -n bench set resources deploy/go-server -c go-server --requests=cpu=500m --limits=cpu=500m
   kubectl -n bench exec deploy/go-server -- cat /sys/fs/cgroup/cpu.max      # "50000 100000"
   ```
2. Re-run the **cpu** scenario. Compare RPS and p99 with the 2-CPU run; check `cpu.stat` — `nr_throttled` grows fast. Go's GOMAXPROCS follows the limit (1), so it degrades gracefully; try the same on fastapi-server (`PY_WORKERS` becomes 1).

**Recover:** `make k8s-up OVERLAY=bench`

## Check yourself
<details><summary>Why do many teams drop CPU limits but keep memory limits?</summary>

CPU is *compressible*: without a limit a pod just competes by its request weight, and spare cycles aren't wasted — while limits cause throttling latency spikes even when the node is idle. Memory is *incompressible*: an unbounded pod can push the whole node into OOM and take neighbours down, so the limit protects everyone. For **benchmarks** we keep CPU limits anyway: fairness between Go and Python means both get exactly 2 CPUs, matching Compose.
</details>

<details><summary>Why must the initContainers have requests == limits too?</summary>

QoS is computed over all containers of the pod. One Burstable init container makes the whole pod Burstable. (The pod's effective request is max(largest init container, sum of app containers), so the 100m init doesn't add to the budget.)
</details>

<details><summary>The node has 12 CPUs and we request ~9.7. What happens to a pod that needs 3 more?</summary>

It stays `Pending` with `0/1 nodes are available: 1 Insufficient cpu`. The scheduler only counts requests, never actual usage — even if the node is 90% idle. Try it: `kubectl -n bench set resources deploy/dashboard -c dashboard --requests=cpu=4` and then roll a server (`kubectl -n bench rollout restart deploy/go-server`): the surge pod is Pending and the rollout never finishes. Recover with `make k8s-up OVERLAY=bench`.
</details>
