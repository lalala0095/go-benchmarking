# K8 — Rollouts

**Goal:** update a Deployment under load with zero errors, and know which knob protects you from what.

## What this repo teaches here
In every Deployment (`base/*/deployment.yaml`):
- `strategy: RollingUpdate` with `maxSurge: 1, maxUnavailable: 0` — a new pod must be Ready before an old one is removed.
- `lifecycle.preStop.sleep: {seconds: 5}` — the native sleep action (the distroless Go image has no `sleep` binary).
- `terminationGracePeriodSeconds: 30` — preStop (5 s) + ~25 s for the server to drain in-flight SSE after SIGTERM.

## Concepts
- **Pod shutdown is a race**: on delete, the kubelet starts preStop → SIGTERM, *while in parallel* the endpoints controller removes the pod from EndpointSlices and every node's kube-proxy (and Traefik) update their routing. Without the preStop sleep, the server can close its listener while traffic is still being sent to it → connection refused / 502.
- **Rollout history**: each pod-template change = a new ReplicaSet revision; `rollout undo` scales the previous one back up.
- `kubectl rollout restart` = patch an annotation (`kubectl.kubernetes.io/restartedAt`) on the template ⇒ new revision, same image.

## Try it
```bash
kubectl -n bench rollout restart deploy/go-server
kubectl -n bench rollout status  deploy/go-server     # "Waiting for 1 old replicas to be terminated…" → "successfully rolled out"
kubectl -n bench get rs -l app.kubernetes.io/name=go-server   # old RS at 0, new at 1
kubectl -n bench rollout history deploy/go-server
kubectl -n bench rollout undo deploy/go-server --to-revision=1
kubectl -n bench get events --sort-by=.lastTimestamp | tail -20   # Killing / Started / Pulled sequence
```
Then run the **rollout-disruption** scenario (chat-mock c=50, rollout at t=15 s): record errors and p99 for Go and Python.

## Break it on purpose
1. Remove the safety nets on go-server:
   ```bash
   kubectl -n bench patch deploy go-server --type=json -p '[
     {"op":"replace","path":"/spec/strategy/rollingUpdate/maxUnavailable","value":1},
     {"op":"replace","path":"/spec/strategy/rollingUpdate/maxSurge","value":0},
     {"op":"remove","path":"/spec/template/spec/containers/0/lifecycle"}]'
   ```
2. Re-run **rollout-disruption**. With 1 replica, `maxUnavailable: 1, maxSurge: 0` means "kill first, then start": a window with *no* Ready pod. Without preStop you also see connection errors at the moment of SIGTERM. Compare error counts with the previous run.

**Recover:** `make k8s-up OVERLAY=bench` (or the overlay you were on).

## Check yourself
<details><summary>What happens to an open SSE stream during a rollout?</summary>

The pod is removed from endpoints (no *new* streams), preStop sleeps 5 s, then SIGTERM. A well-behaved server stops accepting, lets in-flight streams finish (or ends them with a final event) within the grace period, then exits. If it's still running at 30 s, SIGKILL cuts the TCP connection and the client sees a truncated stream. Kubernetes can't migrate a connection — the client must reconnect, and the new request lands on a new pod. A long-lived stream longer than the grace period *will* be cut; that's a design constraint (keep streams short or make clients resume).
</details>

<details><summary>Why sleep in preStop instead of making the app wait?</summary>

Either works; the app could also delay closing its listener after SIGTERM. preStop keeps that policy in the platform config, works for any image, and the native `sleep` action needs no binary in the image.
</details>

<details><summary>Why <code>maxSurge: 1, maxUnavailable: 0</code> and not the default 25%/25%?</summary>

The defaults are 25%: maxSurge rounds **up**, maxUnavailable rounds **down**. With 1–3 replicas that happens to give 1 / 0, but at 4 replicas maxUnavailable becomes 1 and the HPA can change the count at any time. Explicit values state the intent ("never lose capacity") independent of the replica count. The cost: room for one extra pod's CPU *request* during every rollout (bench overlay: 10 + 2 = 12 CPUs, exactly the node).
</details>
