# K9 — Autoscaling

**Goal:** let Kubernetes add server pods under load, and judge whether CPU is the right signal for this workload.

## What this repo teaches here
- `overlays/scale/kustomization.yaml` — stacks on `bench`, shrinks servers to 1 CPU / 512Mi (Guaranteed), dashboard to 3 CPUs, and **removes `spec.replicas`** with a JSON patch so `kubectl apply` doesn't fight the HPA. The CPU-request budget is in the comments: 2 + 3 + 4×1 + 1 = 10 ≤ 12.
- `overlays/scale/hpa.yaml` — `autoscaling/v2` HPAs for both servers: min 1, max 4, target 70% average CPU utilization.
- `scripts/apply.sh` — deletes leftover HPAs when you switch back to `dev`/`bench` (apply never deletes objects).
- The dashboard's Role allows `horizontalpodautoscalers` create/patch/delete: the **scale-out** scenario tunes HPAs at runtime.

## Concepts
- **metrics-server** (bundled with k3s) scrapes the kubelets every ~15 s and serves `metrics.k8s.io` (`kubectl top`).
- **HPA algorithm**: `desired = ceil(current × currentMetric / target)`, using the average over Ready pods, ignoring changes within a 10% tolerance. Utilization = usage ÷ **request**.
- **Stabilization**: scale-up reacts immediately (default window 0 s); scale-down uses the highest recommendation of the last 300 s, to avoid flapping. Tunable under `spec.behavior`.

## Try it
```bash
make k8s-up OVERLAY=scale
kubectl -n bench get hpa
#   NAME             REFERENCE                   TARGETS        MINPODS   MAXPODS   REPLICAS
#   go-server        Deployment/go-server        cpu: 1%/70%    1         4         1
#   (TARGETS shows <unknown> for the first ~30 s until metrics-server has data)
kubectl -n bench get hpa -w            # leave running, then start the scale-out scenario in the dashboard
kubectl top pods -n bench
kubectl -n bench describe hpa go-server | sed -n '/Events/,$p'   # "New size: 3; reason: cpu resource utilization (percentage of request) above target"
```
Record: time to first scale-up, time until the new pod is Ready (Go's static binary vs Python imports), and replicas needed for the same RPS.

## Break it on purpose
1. Remove the CPU request from go-server (limits only ⇒ Kubernetes defaults request = limit, so remove the limit too):
   ```bash
   kubectl -n bench patch deploy go-server --type=json -p '[
     {"op":"remove","path":"/spec/template/spec/containers/0/resources/requests/cpu"},
     {"op":"remove","path":"/spec/template/spec/containers/0/resources/limits/cpu"}]'
   ```
2. `kubectl -n bench get hpa go-server` → `TARGETS cpu: <unknown>/70%`, and `kubectl -n bench describe hpa go-server` shows `FailedGetResourceMetric … missing request for cpu`. The HPA does nothing.

**Recover:** `make k8s-up OVERLAY=scale`. When done with K9: `make k8s-up OVERLAY=bench` removes the HPAs again.

## Check yourself
<details><summary>Why can't the HPA compute utilization without a CPU request?</summary>

Utilization is a percentage *of the request*: 700m used ÷ 1000m requested = 70%. With no request there's no denominator. (You could switch the metric to `type: AverageValue` with an absolute target like `700m`, which doesn't need requests.) And if a container sets a limit but no request, Kubernetes copies the limit into the request — that's why the break step removes both.
</details>

<details><summary>Is CPU the right scaling signal for an LLM-bound service? What would be better?</summary>

Mostly not. A real LLM call is I/O-bound: the server waits seconds for Gemini while using almost no CPU, so CPU stays low while latency and open streams explode (and the bottleneck may be the upstream API quota anyway, which more pods can't fix). Better signals: **concurrency / in-flight requests per pod** (e.g. active SSE streams), **request queue depth or wait time**, or latency SLO burn — exposed as custom metrics (Prometheus Adapter) or via KEDA. CPU works in our *mock* scenarios because token streaming and JSON work are CPU-bound — which is exactly what makes the Go-vs-Python comparison interesting there.
</details>

<details><summary>Why remove <code>spec.replicas</code> from the Deployment when an HPA manages it?</summary>

The HPA writes `replicas` through the scale subresource. If the manifest also sets `replicas: 1`, every apply resets it to 1 (scale-in mid-run), and with server-side apply the two managers conflict over the field. Leaving it out of the manifest makes the HPA its only owner.
</details>

<details><summary>Both targets at 4 replicas: what happens?</summary>

Requests would be 2 + 3 + 4 + 4 = 13 > 12: the last pods stay `Pending` (`Insufficient cpu`). The HPA keeps asking for them, but the scheduler can't place them. Our budget assumes one target scales at a time; on a real cluster the Cluster Autoscaler would add a node.
</details>
